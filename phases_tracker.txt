PHASE 2: Company and administrator registration — [COMPLETE]
 - Company + first COMPANY_ADMIN registration transaction (CompanyController/CompanyService, CompanyStatus), admin login, dashboard shell, hashed-API-key issuance (CompanyApiKeyService).
 - Email verification/activation: reused the AccountInvitation token mechanism (new InvitationPurpose.COMPANY_EMAIL_VERIFICATION) instead of a parallel token table — new admin users are created UserStatus.PENDING (AuthService/JwtAuthenticationFilter already block non-ACTIVE login) and an invitation is issued at registration. New AccountInvitationService.verifyEmail(rawToken) activates the account without touching the password (unlike acceptInvitation, which also resets one), exposed via public POST /api/auth/verify-email.
 - Initial CompanyIntegration record: minimal stub entity/migration (V26 — id, company_id, status only) seeded with NOT_CONFIGURED at registration. Deliberately scoped down — full config fields (API URL, auth, encrypted credentials, retry policy, webhook signing) are added by Phase 6 extending this same table, not reshaping it.
 - RegisterCompanyResponse converted from a Lombok @Data class to a record (per DTO convention) and now returns the raw verification token/expiry directly in the response — same "no email delivery worker yet" pattern already used for ambassador invitations (Phase 4); register.component.ts surfaces it in the post-registration alert so the flow isn't a dead end.
 - Tests: CompanyServiceTest updated for the new PENDING status, CompanyIntegration seed row, and issued verification token; AccountInvitationServiceTest covers verifyEmail's happy path, wrong-purpose rejection, and expiry rejection.
 - Known follow-up (not blocking, mirrors the existing ambassador-invitation gap): no dashboard page yet consumes /api/auth/verify-email — redemption is manual until Phase 13's email worker + a verification UI exist.
 - Bug found and fixed while verifying this end-to-end (live-tested against a throwaway MySQL 8.4 container, not just unit tests): ApiKeyAuthenticationFilter keeps its own hardcoded public-path allowlist, separate from and out of sync with SecurityConfig's permitAll() matchers. Because this filter runs ahead of Spring Security's AuthorizationFilter, a path missing from its list gets a hard 401 "Missing or invalid API key" before permitAll ever applies. This silently broke two endpoints earlier phases had marked complete: POST /api/ambassador-applications/apply (Phase 4) and POST /api/referral-links/{token}/leads (Phase 5) were both unreachable by real unauthenticated callers despite passing their MockMvc-level security tests (those tests exercise SecurityConfig's rule directly, not this filter's separate list). Added /api/auth/verify-email, the apply path, and the leads path to ApiKeyAuthenticationFilter.isPublicEndpoint(); confirmed via live curl smoke test (register -> blocked login -> verify-email -> successful login -> successful anonymous apply).

PHASE 3: Campaign management — [COMPLETE]
 - Prior baseline: Campaign entity/migration (V2), basic create/list/get (CampaignController/CampaignService), company-scoped access.
 - Full lifecycle state machine (V27 migration): CampaignStatus is now DRAFT, SCHEDULED, ACTIVE, PAUSED, EXPIRED, CLOSED, ARCHIVED (dropped the unused CANCELLED, pre-existing rows backfilled to CLOSED). New campaigns start DRAFT; CampaignService.publishCampaign/pauseCampaign/resumeCampaign/closeCampaign/archiveCampaign each enforce the plan's transition rules (e.g. publish computes SCHEDULED vs ACTIVE from the start date; resume rejects a campaign whose referral window already passed) via new POST .../publish|pause|resume|close|archive endpoints on CampaignController.
 - Separate ambassador-enrollment window from the customer-referral window: added ambassador_enrollment_start/end columns (V27, backfilled from existing start_date/end_date so old rows keep today's single-window behavior); CreateCampaignRequest/UpdateCampaignRequest/CampaignResponse carry both windows. Campaign.isEnrollmentOpen() intentionally allows SCHEDULED as well as ACTIVE - the entire point of a separate enrollment window is recruiting ambassadors before the referral period goes live, a bug caught by live end-to-end testing (see below) and fixed before completing the phase.
 - Public non-sequential campaign code + join link: campaign_code (V27, unique, random via new CampaignCodeGenerator, backfilled deterministically for pre-existing rows) plus `{baseUrl}/join/{campaignCode}` in every CampaignResponse. New public, unauthenticated PublicCampaignController (GET /api/campaigns/join/{campaignCode}) resolves a code to company/campaign display info + enrollmentOpen + a human-readable unavailableReason; a DRAFT campaign's code is deliberately treated as not-found so it isn't discoverable before publish. Left the existing public ambassador-application endpoint (Phase 4) untouched by design - the join-link page is expected to resolve the code first, then submit through that existing companyId-based /apply endpoint, so campaign-scoping wasn't grafted onto the intentionally company-wide applications flow.
 - Campaign expiration worker: new CampaignExpirationWorker (`app.campaign.expiration-enabled`/`expiration-interval-ms`, same @ConditionalOnProperty + disabled-in-tests shape as the Phase 6 outbox dispatcher) applies SCHEDULED→ACTIVE and ACTIVE/PAUSED→EXPIRED on a poll loop via CampaignService.activateScheduledCampaigns/expireDueCampaigns.
 - Admin CRUD completed: new PUT .../campaigns/{id} (UpdateCampaignRequest, partial). Reward-rule protection chosen over building a snapshot table now (explicitly deferred to Phase 8/10 per prior tracker note, confirmed with the user): rewardType/referrerRewardValue/refereeRewardValue/conversionEventName/startDate can only change while a campaign is DRAFT - CampaignService rejects the attempt with a clear error otherwise, so RewardService (which still reads these fields live off Campaign) can't have history rewritten under it.
 - Frontend: campaign.model.ts/campaign.service.ts updated to the new contract (enrollment window fields, UpdateCampaignRequest, lifecycle transition calls, PublicCampaignResponse); campaign-form.component.ts gained the two enrollment-date fields; campaign-detail.component gained a "Campaign settings" panel (status badge, both windows, copyable join link, and publish/pause/resume/close/archive buttons gated by campaign status). `ng build` and `tsc --noEmit` both clean.
 - Tests: new CampaignServiceTest (28 cases - creation validation, update field-locking, every lifecycle transition and its rejections, both expiration-worker methods, join-link resolution including the SCHEDULED-enrollment case); CampaignControllerSecurityTest extended for a lifecycle endpoint; ReferralLinkRepositoryTest updated for the new required Campaign columns. Full suite: 149/150 pass (the 1 failure is the pre-existing unrelated ReferralProApplicationTests wrong-package smoke test).
 - Live-verified against a throwaway MySQL 8.4 container (not just unit tests): V27 applied cleanly on top of V1-V26; full create→publish→pause-rejected→close→archive→join-link cycle exercised over HTTP; caught and fixed the SCHEDULED-enrollment bug above via this live run before calling the phase done; confirmed reward-field lock and name-only edit both behave correctly once a campaign leaves DRAFT.
 - Bug found and fixed while live-verifying (same class of gap as Phase 2's finding): the new public /api/campaigns/join/{campaignCode} path had to be added to both SecurityConfig's permitAll() matchers AND ApiKeyAuthenticationFilter's separate hardcoded public-path allowlist - done proactively this time based on the Phase 2 lesson, but it reconfirms that allowlist is a standing footgun for every future public endpoint (see Phase 2's note; worth consolidating into one source of truth eventually, not fixed here as it's out of this phase's scope).

PHASE 4: Ambassador onboarding — [COMPLETE]
 - Prior baseline: Foundation Fix (Ambassador Invitation Flow - one-time invitation-token flow replacing undeliverable temp passwords) and Ambassador Applications (public apply endpoint + admin review/approve/reject, V24 migration, wired to the outbox) - both company-wide, not campaign-scoped.
 - Closed the scope gap noted after Phase 3 landed the public campaign-code join link. Design decision confirmed with the user: extend the existing admin-approval application flow to be campaign-aware rather than build a second, parallel self-service registration mechanism - keeps the one ambassador-onboarding pattern already built, tested, and used everywhere else, rather than bypassing admin review for campaign-link signups only.
 - AmbassadorApplication gained a nullable `campaign` reference (V28 migration) - set when the applicant came through a campaign's join link, null for the company-wide path. POST /api/ambassador-applications/apply now accepts an optional `campaignCode` query param alongside the existing `companyId`; when present, CampaignService.getCampaignForEnrollment(campaignCode, company) hard-validates the code belongs to that company, isn't DRAFT, and has enrollment actually open - rejecting the submission outright (unlike the graceful resolveJoinLink used for read-only link display) if not. Applications now surface campaignId/campaignName in both the admin summary and detail responses.
 - Auto-assignment on activation, not on approval: an approved application's ambassador is still PENDING/INVITED until they redeem their invitation token, and CampaignAssignmentService's bulk-assign precondition (ambassador must already be ACTIVE) correctly doesn't fit a brand-new account. So the campaign assignment + referral link are created in AmbassadorAdminService.activateInvitedAmbassador (right after the profile flips ACTIVE), not in AmbassadorApplicationService.approveApplication. Extracted the assignment+referral-link creation that used to be inline in CampaignAssignmentService.assignAmbassadors into a shared createAssignmentAndLink(...) helper, reused by a new autoAssignFromApplication(...) entry point that skips the active-ambassador precondition (correctly - a fresh account can't already be assigned to anything) and has no CurrentUserService dependency (this runs from the public, unauthenticated accept-invitation flow, so there's no admin principal in context; assignedBy is resolved from the approving admin recorded on the application instead).
 - Frontend: new public, unauthenticated /join/:campaignCode route (CampaignJoinComponent) - the first real UI consumer connecting Phase 3's join link to Phase 4's application flow: resolves the link, shows a controlled unavailable state with the reason when enrollment isn't open, otherwise renders the application form and posts through the new AmbassadorApplicationService (campaignCode passed through automatically). `ng build` and `tsc --noEmit` both clean.
 - Tests: CampaignServiceTest-adjacent coverage via new AmbassadorApplicationServiceTest cases (campaign attached when code resolves and enrollment is open; submission rejected when enrollment is closed); new AmbassadorAdminServiceTest cases for both branches of activateInvitedAmbassador (auto-assigns when the application has a campaign, correctly does nothing when it doesn't). Full suite: 153/154 pass (the 1 failure is the pre-existing unrelated ReferralProApplicationTests wrong-package smoke test).
 - Live-verified end-to-end against a throwaway MySQL 8.4 container, not just unit tests: full chain of register → verify → login → create+publish campaign → resolve join link (enrollmentOpen:true) → submit application with campaignCode → admin approves → ambassador accepts invitation → ambassador logs in and GET /api/ambassador/campaigns shows the auto-created assignment with a live, working referral link (http://localhost:8080/r/{token}) - all without any manual "assign ambassador to campaign" step. V28 confirmed applying cleanly on top of V1-V27.

PHASE 5: Referral attribution and end-user registration — [COMPLETE]
 - Foundation Fix: Referral-Link & Click-Attribution Correctness — route /r/{token} through ReferralLink.publicToken, decouple click recording from requiring an existing Referral, populate previously-unset ReferralClick attribution fields.
 - Public Referred-Customer Journey (V25 migration): public POST /api/referral-links/{token}/leads (unauthenticated) turns a ReferralLink click into a Referral in REGISTERED status.
 - Attribution-session linkage via shared AttributionSession helper (rp_attr_session cookie) used by both ReferralRedirectController and ReferralLeadController; same-session resubmission is idempotent, cross-session duplicate email against the same link is rejected (excluding terminal statuses).
 - Lead identity reuses PlatformUser via a synthetic externalUserId (SHA-256 of email) — no new identity table.
 - Publishes referral.lead_registered via OutboxEventPublisher.
 - Defensive guard added in ConversionService for the now-reachable referrerUser == null state.
 - Note: writing an outbox row that triggers the company Create User API call is Phase 6 scope, not this phase's — confirmed still correctly out of scope, not a gap.
 - Gap found and closed after this phase originally shipped (before Phase 3's campaign lifecycle existed): neither ReferralClickService nor ReferralLeadService ever checked the owning campaign's status, only ReferralLink.status/expiry — ConversionService already gated on campaign.isActive() so conversions were safe, but pausing/closing/expiring a campaign left its ambassadors' referral links silently still accepting clicks and lead submissions.
 - Fixed by cascading campaign lifecycle transitions onto ReferralLink status in CampaignService: pauseCampaign/closeCampaign/expireDueCampaigns/archiveCampaign now disable each campaign's ACTIVE referral links (disableActiveReferralLinks), resumeCampaign re-enables the ones it disabled (reactivateDisabledReferralLinks). Both filter on CampaignAmbassadorAssignment.status = ACTIVE (new ReferralLinkRepository.findByCampaignIdAndStatusAndAssignment_Status), not just link status - this is what stops a link an admin already disabled by individually removing that ambassador (CampaignAssignmentService.removeCampaignAssignment) from ever being wrongly swept back to ACTIVE just because the campaign itself resumes.
 - Tests: 5 new CampaignServiceTest cases covering the disable/reactivate call on each of pause/resume/close/expire, plus explicit verification that resume only ever queries assignment-ACTIVE links. Full suite: 157/158 pass (the 1 failure is the pre-existing unrelated ReferralProApplicationTests wrong-package smoke test).
 - Live-verified end-to-end against a throwaway MySQL 8.4 container (confirms the Spring Data nested-property query works against real SQL, not just mocks, and that the new CampaignService -> ReferralLinkRepository dependency doesn't introduce a bean-wiring cycle): full chain of create+publish campaign → apply/approve/activate an ambassador via campaignCode → click the resulting referral link (302 redirect) → pause the campaign → same click now 404s ("Referral link not found") → resume the campaign → same click redirects again (302).
